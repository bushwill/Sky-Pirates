# Flagstrike rooms

## Runtime architecture: data-only server, host-computed matches

The production server runs in host-authoritative mode. It is responsible for WebSocket connections, room/lobby membership, player/session metadata, host election, and bounded, rate-limited data relay. It does not run a gameplay ticker, generate/search maps, adjudicate combat, or decide match outcomes. It stores the latest host frame for reconnects and host handoff, and runs only room/lobby lifecycle timers.

The elected host's browser performs map generation and competitive map search, initializes the match, runs bot AI, resolves gameplay actions, and publishes complete sequenced state frames. Each client simulates and sends sequenced state for its own player; the host simulates unclaimed bots and its own player, then uses owner-sent player states for shared combat and collision. Bot takeover uses the same owner-state path while the host retains authority over bot combat, gadgets, and match outcomes. Client prediction is for responsiveness, not a second source of shared match truth. The server routes gameplay messages and retains host-produced frames as room data. It enforces transport size/rate limits and host-frame protocol ordering, but does not validate or compute player movement, combat, or gameplay outcomes; owner-state checks and simulation run in the game clients.

Movement and host-world updates use a 60 Hz fixed-step accumulator. A bounded number of steps run per render frame, and unprocessed elapsed time remains queued rather than being discarded when the host is briefly busy.

`game:host-frame` is the live state protocol, not just a helper: the host publishes complete sequenced frames no more often than every 25 ms (up to about 40 Hz), the server validates the envelope and retains/relays the latest complete snapshot, and clients apply newer frames. Team-private exploration and pings are routed only to the relevant team. Map search and generation happen in the host browser; the server stores the submitted map as room data so it can be included in the lobby/match handoff.

The host also calculates transient gunshot and footstep cues. It sends each cue only to the opposing team that can hear it, keeps its approximate location in bot team intel, and expires it without persisting private sound events in shared room snapshots. Footsteps are generated in the live host simulation, not by the legacy server-side gameplay path.

Host-frame events are drained in protocol-sized batches and briefly replayed so transient tracers and team-private prop damage can recover from a missed relay. Mine effects remain private to the host simulation and are merged with each recipient's team intel across ordinary snapshots. Vision originates at the player's position and tracks the aim pointer independently of the weapon's turn rate.

### Adaptive client workload

The client smooths the time spent in each game update and classifies it as LOW (<4 ms), MEDIUM (4–10 ms), or HIGH (≥10 ms). This measures client update computation, not network round-trip latency. The computation indicator is green, yellow, or red for those levels.

Adaptive scheduling protects gameplay work and reduces lower-priority work first:

- The controlled actor continues to simulate every render frame with the 60 Hz fixed-step movement clock. Owner input is sent every 25 ms or sooner when input changes. Controlled-player vision refreshes within 50 ms of a vision-input change, and weapon/gadget actions remain event-driven.
- The aiming cursor uses the browser/OS crosshair over the game canvas rather than a cursor redrawn in the game-update loop, so pointer movement remains smooth and independent of adaptive game work. Hit-confirmation marks remain a separate short-lived game effect.
- Remote actors continue receiving host-frame state (up to about 40 Hz) and are interpolated every render frame. The adaptive scheduler does not slow player state replication or interpolation.
- High-frequency host-frame-driven inventory HTML rendering is capped at 20 Hz in LOW/MEDIUM and 10 Hz in HIGH; lower-priority match HUD rendering is capped at 20/10/5 Hz. Scoreboard updates are independent of that match-HUD throttle and render when scoreboard data changes. Match state and events are still applied immediately; discrete room/game-state transitions still render immediately.
- The client-compute HUD shows only `CLIENT COMPUTE LOW`, `CLIENT COMPUTE MEDIUM`, or `CLIENT COMPUTE HIGH`. Full frame, host publish/receive, host-frame application, revision-gap, and phase timings remain available in the copyable console object; compare host TX with client RX to distinguish slow host publishing from relay/client delivery.
- Host-frame snapshot application skips its immediate player render because the next game frame renders the updated state. Player gun geometry and unchanged name/health/armor display state are reused, and idle reload-arc graphics are not cleared every frame. Performance snapshots split player visibility checks, marker updates, and flag rendering.
- Enemy visibility checks reuse their result for at most 50 ms while a player stays within one body-radius of the checked position; vision changes and larger position jumps invalidate it. Player-circle visibility uses overlap against the existing vision polygon rather than issuing repeated per-sample wall raycasts.
- Vision geometry reuses its combined map-and-active-smoke object list until the map or smoke state changes or a smoke expires, avoiding repeated filtering and JSON-signature allocation during the render/update loop.
- Destructible-prop visibility scans are lower-priority work and adapt to 100/150/250 ms intervals in LOW/MEDIUM/HIGH. Damage, destruction, and map changes still force an immediate redraw; controlled-player vision and player replication are not throttled by this policy.
- Teammate vision is the primary adaptive workload. On each update, living teammates are ranked by physical distance to the controlled actor. Rank 0 is the closest teammate (excluding the controlled actor); subsequent ranks receive progressively slower refreshes. In LOW, intervals are 50 ms + 25 ms per rank; in MEDIUM, 100 ms + 75 ms per rank; in HIGH, 200 ms + 200 ms per rank, capped at 1 second. A per-frame rebuild budget of 5/2/1 teammate visions respectively spreads expensive work and favors the closest due teammate. The controlled actor's 50 ms vision cadence is not reduced.

Weapon projectile collision radii are 0.1 world units; gadget radii remain gadget-specific. Gadget damage cues point toward the damaging gadget/effect while kill and assist credit remains attributed to its owner. Mine intel is relayed independently for each team. While a match is active, the client logs one structured object with `type: 'game-performance'` per second, including full copy/paste performance metrics; other routine gameplay diagnostics are not written to the console, and actionable failures use error logging.

### Scope and migration notes

The production entry point explicitly selects host-authoritative mode and no longer calls `RoomManager.advanceGames()` or server-side combat/gadget/objective handlers. Some legacy server-authoritative methods remain in `RoomManager.mjs` for existing unit-test compatibility, but they are not used by `server.js`. The host-side simulation is the runtime authority; partial prop damage and prop destruction is shared with all players. Do not add gameplay calculations back to server request handlers or lifecycle timers.

## Room behavior

- Rooms are temporary, case-insensitive by name, and removed when their last client leaves.
- Creating a room joins its creator immediately. A room can be open or protected by an optional password.
- Passwords are never stored or returned in room listings; the server stores a random-salt scrypt hash.
- Room names are limited to 32 letters, numbers, spaces, hyphens, or underscores. Passwords are limited to 128 characters.
- The server currently allows up to 256 active rooms and 64 clients in each room.
- The first player to create a room is its host. An explicit host leave immediately elects the earliest-connected player; a lost connection is retained for up to 15 seconds to allow session resume before host election. Host handoff preserves the latest match state and deadline while removing the departed player from the retained frame.
- Every room member is automatically assigned to the less-populated Strike Team or Flag Team on joining. Their home objectives are the Strike Site and Flag Site. Players can switch teams while the destination has capacity; the host can swap two players when both teams are full. There is no unassigned team group.
- Map selection settings and submitted maps are room data; the host browser runs map generation and competitive-map search. Candidate maps remain hidden until accepted and revealed for match start. Practice and Quick Play use the same ready-up lobby, host-side map preparation, bot roster, countdown/result/report phases, and role/score metadata.
- During custom and Practice countdowns, players may choose a weapon and gadget only. Quick Play uses its separate multi-pick offer shop, including armor and perks; it presents six offers in the first shop and five in each subsequent shop. Purchases are retained in the accepted host state through the countdown.
- Unique gadgets are marked with `rarity: 'unique'` in `shared/GadgetModel.js`. Real-player offers begin at 1% per shop, increase by two percentage points per subsequent shop, and cap at 10%; bots are excluded from these offers. When the unique-offer chance hits, Quick Play randomly selects from all existing unique gadgets. Unique gadgets appear in a separate loadout tab; Orbital Strike, Spy Camera, Vine Trap, Sonar, Katana, and Trophy System are available in custom and Quick Play loadouts. Bots can also receive and use each unique gadget: they target Orbital Strikes with visible or team-reported enemy positions, face Spy Cameras toward threats or their route, place Vine Traps on useful routes, send Sonar toward enemy sightings/audio or along their current map route, dash at nearby visible enemies with Katana, and place Trophy Systems while defending or after advancing toward the flag. Bots shoot visible enemy Spy Cameras and Trophy Systems.
- Trophy Systems are short-thrown without bouncing, last 60 seconds after landing, and can be damaged by enemy gunfire or Molotov fire. They intercept enemy smoke, flash, cryo, Molotov, proximity-mine, and Vine Trap projectiles along an unobstructed line of sight at any range, and destroy enemy Spy Cameras, proximity mines, Vine Traps, and Trophy Systems that are placed in sight. Orbital Strikes destroy all gadget effects in their blast radius, including Trophy Systems. Sonar, Katana, players, and bullets are unaffected by Trophy interception. Gadget projectile speeds are halved except for Sonar.
- Proximity-mine blasts, Molotov fire, and Orbital Strike impacts/fire damage players, destructible props, and nearby placed gadgets. Device health is reduced by the damage; mines and Vine Traps are destroyed when hit. Orbital Strike's immediate blast and subsequent fire both apply area damage.
- Per-charge cooldowns automatically recharge missing charges while the owner is alive; Sonar has two charges, each recharging after 60 seconds alive, while Katana recharges its single charge after 60 seconds alive or immediately after a kill. Sonar's slower, team-visible projectile bounces along an 800-unit path, reveals nearby map and wall intel in line of sight, and listens for nearby footsteps and gunfire. Katana dashes up to 100 units, kills the first enemy within its 40-unit hit radius, and stops at walls and map boundaries; a miss immediately switches back to the gun, while a kill restores the charge and keeps Katana equipped.
- Clients compute local visibility for rendering and relay team exploration data through the server. The server routes those data packets by team but does not calculate vision, fog, shot intel, or visibility.
- Each client simulates its own controlled player or bot, including movement and actions such as aiming, looking, vision, shooting, reloading, and objective interactions. It sends sequenced position and action updates to the elected host, which treats them as owner-authoritative state, combines them, and publishes the synchronized state to other clients through host frames. The host simulates bots with no client owner. Clients smooth or predict remote actors between host frames; they simulate their own controlled actors locally rather than relying on prediction for them.
- WebSocket clients send application heartbeats and the server also uses WebSocket ping/pong. Clients reconnect with bounded exponential backoff and can resume the same room/player session for up to 15 seconds after an interrupted connection. Stale-input handling is performed by the host simulation.
- Matches use a 1500 × 1000 map (width × height)
- Room state is in memory by design: restarting the server clears the room list. Persistent rooms would require a defined product need and durable storage.

## Structure

- `client/src/network/RoomClient.js` owns the WebSocket request/response protocol.
- `client/src/ui/RoomLobby.js` owns accessible lobby controls and room-list rendering.
- `client/src/game/GameView.js` owns the Phaser map, owner-local actor simulation, remote actor smoothing, host movement for unowned bots, state aggregation, rendering, and match timer.
- `server/RoomManager.mjs` owns room validation, membership, passwords, limits, host election, lobby configuration, and opaque latest-frame storage. Legacy simulation methods are not called by the production entry point.
- `server/server.js` owns HTTP/WebSocket transport, keepalive, session resumption, input/action relay to the elected browser host, and host-frame broadcasts. Its one-second timer is limited to lobby/session lifecycle transitions.
- `shared/HostFrameProtocol.js` validates the bounded host-frame envelope; `shared/HostFrameSnapshot.js` creates and applies complete gameplay snapshots while preserving recipient-local intel.

The client sends JSON WebSocket requests with `requestId`, `type`, and `payload`; each request receives a correlated response. Room-list changes use server broadcasts; gameplay snapshots are produced by the elected host and relayed as sequenced, match-scoped frames. Each client simulates its own controlled actor and sends sequenced position and action updates to the host; the host client incorporates those owner-authored states into frames for other clients, while it advances bots with no client owner itself. Clients smooth or predict remote actors between host frames. The server only routes the owner updates and stores/relays the host-produced snapshot. Weapon actions use stable sequence IDs, retry until acknowledged in a host frame, and are processed at most once; owners replay unacknowledged weapon prediction over each host snapshot so visual and ammo state reconcile without waiting for the next input. Resume tokens are stored in session storage and allow a reconnecting browser to reclaim its player session. Passwords and client-provided room metadata are not exposed to other players.

## Tests and deployment

Run server and client model unit tests with `npm test` in `server/` and `client/`. Both test suites also run during their respective Docker builds. The website Compose stack builds and runs the `flagstrike-client` and `flagstrike-server` services; no additional host ports are opened.

The production WebSocket endpoint accepts only `https://bushwill.ca` and `https://www.bushwill.ca` by default. Set `FLAGSTRIKE_ALLOWED_ORIGINS` to a comma-separated list when hosting elsewhere. Local development allows the Vite origins on `localhost:5173` and `127.0.0.1:5173`. The server also caps active WebSockets at 128 globally and 16 per client IP, limits ordinary requests to 120 per minute per IP, and limits room-allocation attempts to 20 per ten minutes per IP. These limits can be adjusted with `FLAGSTRIKE_MAX_WEBSOCKET_CLIENTS` and `FLAGSTRIKE_MAX_WEBSOCKET_CLIENTS_PER_IP`. Keep the Flagstrike server behind the trusted reverse proxy so its forwarded `X-Real-IP` identifies the actual client; these limits do not stop large volumetric attacks upstream of the proxy.
